The SHA-256 and version have been verified from the archived executable. The
binary remains the oracle for historical variable-string behavior.

## Official-build host compatibility

Official libminizinc 2.0.97 was configured with CMake and GCC 13.3.0. Its
bundled parser and lexer cache is used deliberately: Bison 3.8 generates a
parser incompatible with the historical location API. The recovery build
script copies the upstream-provided cached parser and lexer into its ignored
build directory after CMake configuration, ensuring they are newer than their
grammars. The upstream checkout is not modified. This compatibility choice is
unrelated to the historical string extension.

GCC 13 also rejects `flatten.cpp` because it uses `std::numeric_limits` without
including `<limits>`. The script supplies `-include limits` through the build
configuration rather than altering official source. This flag and the cached
parser workaround must not be included in a reconstructed string-extension
patch.

## Initial subsystem map

The recovery work must investigate these compiler subsystems before changing
any source:

| Subsystem | Expected responsibility | Initial confidence |
| --- | --- | --- |
| Type representation | `var string` and compatibility rules | Strong candidate |
| Parser and type instantiation | variable-string declarations and arrays | Strong candidate |
| Type checker | overload resolution and string literal coercions | Strong candidate |
| Evaluation | string sets and constant expressions | Possible candidate |
| Flattening | variable declarations and `str_*` constraints | Strong candidate |
| Builtins | string/array conversion, length, concatenation | Possible candidate |
| Output | FlatZinc and OZN serialization | Strong candidate |

`symbols.txt`, `official-symbols.txt`, and
`custom-symbol-candidates.txt` are generated by the recovery scripts. A
candidate symbol is evidence, not proof of a private extension.
