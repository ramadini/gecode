# Gecode integration design

The target is Gecode 6.4 and its generated variable-implementation mechanism.
The integration is source-level because a new native variable type needs entries
in generated `var-type.hpp` and `var-imp.hpp`.

## Generated type specification

`integration/gecode/gecode/dashed/var-imp/list.vis` defines:

- assignment;
- length-only change;
- structural/domain-only change;
- combined length and structural change;
- propagation conditions for assignment, length, domain, and any change;
- `Dispose: true` because `ListVarImp` contains RAII-managed external payloads.

## Build outline

From a Gecode source checkout, copy or add the integration tree and configure:

```bash
cmake -S . -B build \
  -DGECODE_WITH_VIS=gecode/dashed/var-imp/list.vis \
  -DGECODE_REGENERATE_VARIMP=ON
cmake --build build
```

Generation currently requires the Python/`uv` toolchain described by Gecode's
build documentation.

The Gecode source inventory and exported library target must then include the
Dashed adapter sources. The standalone core can either be built as an object
library inside Gecode or linked as `Dashed::core`.

## Modification-event mapping

```text
dashed::Change::none      -> ME_LIST_NONE
dashed::Change::length    -> ME_LIST_LEN
dashed::Change::domain    -> ME_LIST_DOM
dashed::Change::both      -> ME_LIST_BOTH
dashed::Change::assigned  -> ME_LIST_VAL
dashed::Change::failed    -> ME_LIST_FAILED
```

A domain operation computes its `Change`, creates a small delta if advisors need
one, and invokes the generated `notify(home, me, delta)` exactly once.

## Lifecycle

`ListVarImp` constructor:

- validates a nonfailed domain;
- stores it in-place;
- registers through generated base construction.

Clone constructor:

- invokes `ListVarImpBase(home, other)`;
- copies the `Domain` descriptor;
- shares immutable exact/value-set payloads.

`copy(home)`:

- uses Gecode's forwarding/copy protocol;
- never deep-copies literal buffers.

`dispose(home)`:

- explicitly destroys/reset the `Domain` payload;
- allows generated/base disposal bookkeeping to complete;
- must match the exact signature generated by Gecode 6.4.

The included adapter files are intentionally marked as a blueprint until they
are compiled against a generated 6.4 tree; generated-base signatures should be
taken from that build, not guessed around with casts.

## Views

`ListView` derives from `VarImpView<ListVar>` and forwards:

```text
domain()
assigned()
min_length()
max_length()
value()
replace(home, restricted_domain)
tighten_length(home, lower, upper)
```

It does not expose a mutable pointer to the domain and does not contain
constraint algorithms.

## Propagators

A propagator follows this transaction pattern:

1. read current view domains;
2. copy the small domain descriptors into local values;
3. run the standalone kernel until its own fixpoint;
4. commit each changed domain through the corresponding view;
5. return failure, subsumption, or fixpoint status.

Copying descriptors is safe and cheap because heavy payloads are shared.
Committing only after the pure kernel returns also prevents a kernel from
observing half-updated Gecode state.

## Reification

The standalone `BoolDomain` exists only for kernel testing. Native propagators
should use `Int::BoolView` and Gecode's standard reification modes. The Boolean
side is committed after the pure relation status is known.
